## 怎么跑

```bash
npm install
npm run dev          # http://localhost:5173
npm run build        # 生产构建
```

前端默认走**后端真实接口**（`.env.development` 里的 `VITE_APP_USE_MOCK = false`），
后端地址由同文件的 `VITE_APP_API_TARGET` 指定，vite 代理转发。

> ⚠️ **不要再在注释或文档里维护「后端已实现哪些模块」的清单** ——
> 曾经有过一份，写的是「只实现了 `/health`」，后端补齐后没人回来改，
> 把排查问题的人带偏过。要查实际可用性**用命令**：
> `npm run check:api`、Knife4j 文档页 `http://localhost:8080/doc.html`、
> 以及 `npm run gen:api-status` 生成的 `docs/接口清单.txt`。

`src/mock/` 是**骨架期的假数据**，只在 `VITE_APP_USE_MOCK = true` 时启用，
当前已基本不用（字段口径是旧的中文文本口径，见第 9 条）。
`check:mock` 会强制以 mock 模式跑 api 层，那是它唯一的用途。

### 自检脚本

| 命令 | 作用 |
| :--- | :--- |
| `npm run gen:menu` | 从后端 `sql/crm.sql` 的 `sys_menu` 种子生成 `src/mock/menu.js`。**菜单别手改这个文件，改 SQL 后重跑** |
| `npm run check:api` | 校验前端发的每个请求路径都能在《05-接口文档.md》里找到 |
| `npm run check:mock` | **直测 api 层**：验证 mock 下写操作真的改了数据（78 项断言）|
| `npm run check:static` | 静态审查 `src/**` 共 12 项：表单 `type` 有没有控件、模板事件/组件有没有定义、`FIELDS` 有没有漏进 `emptyForm`、api 写操作的 mock 分支有没有落库、请求能不能静态解析…… |
| `npm run gen:api-status` | 生成 `docs/接口清单.txt`（已完成 / 未完成接口）|

> **后端目录由 `scripts/lib/backend-paths.js` 探测**，五种布局都支持：
> `crm-ui/aurum-crm`、`crm_cp/crm/aurum-crm`、`crm_cp/aurum-crm`、
> `repo/master/crm/aurum-crm`、以及**双层嵌套 `repo/crm/crm/aurum-crm`**（本机当前布局）。
> 实在探测不到时用 `AURUM_BACKEND_DIR=/path/to/aurum-crm` 显式指定。
> 原先 `check:api` / `gen:api-status` / `gen:menu` **各自**写死 `../../aurum-crm` ——
> 后端换个布局就「找不到接口文档」直接 `exit 1`。症状是**自检不可用**而不是「检查不通过」，
> 很容易被当成环境问题跳过，于是自检形同不存在。路径解析只留一份，理由同下面这条。
>
> ⚠️ **这条修复丢过两次，别再丢第三次**（详见后端《07-测试BUG记录》BUG-011 与 BUG-020）：
> 1. 第一次：补了双层嵌套布局，但那份实现在 `backend-dir.js` 里；
>    向 `backend-paths.js` 收敛时**漏抄了这一条**，本机布局又找不到后端了；
> 2. 同一次合并还把**未解决的冲突标记**（`<<<<<<<`）提交进了 `check-api-align.js`，
>    于是 `check:api` 直接 `SyntaxError` 崩掉。
>
> 由此得来的两条规矩：
> - **改完 `scripts/` 下的东西，一定把四个自检脚本都跑一遍** ——
>   只跑一个的话，另一个崩了也不知道；
> - **`scripts/lib/backend-dir.js` 是重复实现，已无人 import，应当删除。**
>   留着它就是在等下一次「只有一份被 import、另一份静默腐烂」。
>
> ⚠️ Windows 上 `check:static` 曾经**从来没能跑起来**：它用
> `execSync('find src -name "*.vue"')` 收集文件，而 PATH 里的 `find` 是 Windows 自带的
> `find.exe`（在文件里搜文本，完全是另一个程序），会以
> 「Access denied - SRC / File not found - -NAME」失败。已改成 `fs` 递归收集，
> 不再依赖任何外部命令（顺带也躲开了 `execSync` 默认用管道捕获输出、在受限 shell 里 EPERM 的问题）。

> `check:api` 和 `gen:api-status` 共用 `scripts/lib/api-calls.js` 里的抽取逻辑。
> **别在两个脚本里各写一份** —— 曾经因为复制了一份，两处都只认引号形式的 url、
> 漏掉 62% 的请求还一直报「全部通过」（详见第 21 条）。

> `check:mock` 是目前**唯一能覆盖 api 层**的检查。它把 api 源码里的 `@` 别名和
> `import.meta.env` 替换掉，写进系统临时目录再 import，从而在 node 里直接调用真实的
> api 函数。加完写接口后跑一下 —— build 是抓不到 `return { ...data }` 这种假成功的。

## 已经踩过的坑（改代码前先看）

1. **菜单两边会漂移** —— 菜单权威源是后端 `sql/crm.sql` 的 `sys_menu`，`src/mock/menu.js` 是**生成的**（`npm run gen:menu`），**别手改 mock 那份**。改造前两边已经不一致（后端叫「线索管理 / 产品类型 / 回款登记 / 组织架构」，原型叫「线索 / 产品 / 财务 / 系统设置」）。
   - ✅ **已对齐**（2026-09-15）：`线索`（10 / 11）、`系统设置`（70）。只改了 `crm.sql` 的种子；
     **存量库没有增量脚本**，需手工跑两条 UPDATE（见后端《02-建表文档》末节）。
   - ❌ **仍不一致**：`产品类型`（50）、`财务`（60）。
   - ⚠️ **改菜单只改 `sql/crm.sql`，然后 `npm run gen:menu`**；存量库另出一个 `alter-*.sql`。
     反例：`menu_id=66`（发票详情）当初只写进了增量脚本、没回填全量脚本，结果**全新装完点发票编号跳详情会落到不存在的路由**，直到 2026-09-15 才补上。

2. **接口文档与原型会不一致，且是双向的** —— 已按「以原型为准、回补文档」处理：文档第九节从 4 个接口扩到 8 个，另补 7 个导出接口。改动前先 `npm run check:api`。

3. **`<transition>` 不能加 `mode="out-in"`** —— 在 Vue 3.5 下配合会变化的 `:key`，新组件不会被插入，内容区渲染成空注释，表现是点导航后页面一片空白。详见 `styles/index.scss` 注释。

4. **导航高亮要用完整菜单树查、侧栏树渲染** —— `composables/useActiveMenu.js`。若用过滤后的侧栏树去查当前路由，`visible=0` 的页面（客户详情、公海规则、操作日志）会匹配不上，导致**左侧栏整条消失**。

5. **`ProList` 的 `detailPath`** —— 只有线索/客户/商机/合同/回款这 5 类有详情页。新增列表页时若没有详情页就不要传 `detail-path`，否则点了名称会跳 404。

6. **mock 的写操作必须真的写数组** ⚠️ —— `createXxx / updateXxx / submitXxx / 上架下架` 在 mock 下都要用 `insertRow / updateById`，否则会弹「保存成功」但数据纹丝不动。这不是小事：本轮之前**所有**写接口都是这个状态。
   - **新增行要 `unshift` 到数组头部**：`queryPage` 按数组顺序分页，追加到末尾的话新行落在最后一页，用户点完保存看不到变化，会以为失败。
   - `insertRow` 会补 `creator / createTime`，列表页大多有这两列，缺了就是一片「--」。

7. **树形数据的增删改别用平铺函数** —— `removeById` 只扫数组顶层，拿它删子部门会**静默失败**（提示删除成功但节点还在）。部门、产品分类一律用 `insertTreeNode / updateTreeNode / removeTreeNode`。
   另外：**编辑树节点前要先摘掉 `children`**，否则 `deepClone` 会把整棵子树复制进表单模型一起提交。

8. **`.el-table .cell` 的 flex 居中会挤坏明细表** —— `element.scss` 里为列表页把单元格统一改成了 `display: flex` + 居中，但明细编辑器的单元格里装的是 `el-input-number`，会被挤成一小段。用 `.crm-items-table` 包住改回 `display: block`。

9. ~~**表单字段口径与后端 DDL 不一致** ⚠️ 最大的技术债~~ —— ✅ **本债已还清**（2026-09-13，详见
   后端 `crm/docs/07-测试BUG记录.md` 的 BUG-002）。下面是现行约定的**权威说明**，加字段前先读这一条。

   ### 三条约定

   **(1) 数据字典字段传码值，不传中文。**
   判断标准：这个字段的取值存在 `sys_dict_data` 表里。
   如 `source` / `industry` / `level` / `dealStatus` / `contractType`。
   - **取数一律走 `composables/useDictOptions.js`**（数据源是 `GET /system/dict-data/batch`）：
     · 表单下拉 → `options: () => dictOptions('crm_source')`（**写成函数**，由 `FormField` 求值）
     · 列表/详情 → `const SOURCE_MAP = useDictMap('crm_source')`，模板里照旧 `SOURCE_MAP[row.source]`
     · 列的 `format` → `dictLabel('crm_source', v)`
   - ⚠️ **不要 import `constants/options.js` 里的 `*_CODE_OPTIONS`**（如 `CUSTOMER_SOURCE_OPTIONS`）。
     那份已降级为「接口失败时的兜底种子」，直接 import 会让下拉永远停在种子值上、
     管理员在字典管理页改了也看不到，**且不报错**。`npm run check:static` 会拦下这种写法。
   - ⚠️ **不要写成 `Object.fromEntries(...)` 常量**（那是快照，字典到达前就定格 → 整列 `--`），
     必须是 `useDictMap()` 返回的 computed。
   - ⚠️ 传中文会让后端 Jackson 反序列化失败 → 500（这正是 BUG-002 的直接原因）
   - ⚠️ 后端 `DictDataRespVO.value` 是**字符串**（`"1"`），而业务 DTO 是 `Integer`。
     转换已在 `useDictOptions` 的 `DICT_VALUE_TYPE` 表里统一做掉，**页面里不要再 `Number()`**；
     新增字典类型时在那张表里登记一行。

   **(2) 状态机枚举字段用中文标签，由后端转。**
   判断标准：取值写死在 Java 枚举里（`OpportunityStage` / `QuotationStatus` /
   `ContractAuditStatus` / `ContractStatus`）。
   - 表单和列表**都用中文**，`opts([...])` 生成的常量即可，前端不做任何映射
   - 后端在 Convert 里用 `labelOf()` 把码值转成标签再返回

   **(3) 请求方向用 DDL 字段名，响应方向的别名由后端补。**
   - 表单 `prop` 写 DDL 名（`leadName` / `contractName`），不写 `name`
   - 列表可以放心用 `id` / `name` / `customerName` / `creator` / `region`
     这些**后端会补齐的别名与派生字段**（`ContractRespVO` 的 `id` 别名曾经缺失，
     后果是详情跳到 `/crm/contract/undefined` 且不报任何错）

   ### 两个具体口径

   - **地区**：表单与列表只跟拼接串 `region` 打交道；
     提交时由 **api 层**的 `splitRegion()`（`api/customer.js` / `api/lead.js`）
     拆成 `province` / `city` / `district`；响应方向的 `region` 由后端派生好再返回。
     **新增带地区的模块时，记得在对应的 api 文件里也加一份 `splitRegion`。**
   - **金额**：合同的 `finalAmount` 映射自后端的 `amount`（含税）；
     「整单利润」全库无 `profit` 列，这一版不计算利润，相关列已移除。

   ### 仍未对齐的部分

   `src/mock/db.js` 与 `src/mock/menu.js` 是**已废弃的本地 mock 数据**，
   取值还是旧的中文口径。当前 `VITE_APP_USE_MOCK=false`，它只在 `check:mock` 里被用到。
   旧的中文常量（`SOURCE_OPTIONS` / `INDUSTRY_OPTIONS` / `CUSTOMER_LEVEL_OPTIONS` /
   `CONTRACT_TYPE_OPTIONS`）已标 `@deprecated`，确认无引用后可以删除。

10. ~~**选择器接口的契约缺口**~~ —— ✅ **已解决**。`/simple-list` 的响应比文档第十节约定的 `{ id, name, extra }` 更宽：后端各模块的 `XxxSimpleRespVO` 直接给了编辑器要的字段（如 `ProductSimpleRespVO` 带 `unitName` / `salePrice` / `costPrice` / `taxRate`），不需要为 `extra` 再定格式，也不用懒调详情接口。
    - 报价单选择器同理：`QuotationSimpleRespVO` 每行**还带 `products`**（含跨表补好的 `unitName`）、
      `opportunityId` / `opportunityName` / `customerId`，并支持按 `opportunityId` / `customerId` 收窄；
      商机选择器（`OpportunitySimpleRespVO`）也带 `customerId` 与 `products`。
      合同表单选中商机/报价单后用它**整份**回填产品明细与客户/商机（`views/crm/contract/form-config.js`），
      所以**不要**为了拿明细再调一次 `GET /crm/quotation/{id}`。

11. **`el-form` 不会自动校验自定义组件** —— `EntitySelector / RegionCascader / DeptTreeSelect / ProductItemEditor` 变更时 `el-form-item` 收不到 change 事件。校验基线放在提交时的 `formRef.validate()`，别把「必填红星实时变红」当验收条件。

12. **弹窗不要用 `destroy-on-close`** —— 销毁重建会带来校验状态残留和赋值时序竞争。用 `watch(visible)` + 深拷贝回填 + `nextTick(clearValidate)`，行为确定得多。

13. **编辑回填优先用列表行，别无脑调详情接口** —— `ProList` 的 `@action` 已经回传了完整行对象（`rows: selection.value`），只有两类必须调详情：列表行里根本没有的数据（报价单/合同的明细行）、列表列没展示的字段。

14. **回填必须深拷贝**（`useFormDialog` 里已经做了）—— 直接用列表行对象的话，表单里没有 v-model 绑定的字段会原地改到列表行上，用户点「取消」后表格里的值已经变了。用 JSON 往返而不是 `structuredClone`，项目里日期全是字符串，行为更可预测。

15. **`queryPage` 会对任何未识别的查询参数做等值过滤** —— 给表单/接口加新字段是安全的，但**新字段名不要与 `keyword` / `scope` / `status` / `pageNo` / `pageSize` 重名**。同理 `getUserPage` 会把 `status` 翻译成 `accountStatus / workStatus`，人员表单不要用 `status` 作字段名。

16. **`contractAudit` / `paymentAudit` / `invoiceIssue` / `customerPool` / `leadPool` 是模块加载时生成的快照**（**仅 mock 模式**，`VITE_APP_USE_MOCK = true`）—— 改主表不会同步，编辑合同后去「合同审核」页看数据还是老的。
    当前 `VITE_APP_USE_MOCK` 为 `false`，走真实后端，**不会遇到这个现象**；这条只在你切回 mock 调试时成立。

17. **金额口径** —— 《02-建表文档》3.6 定义 `total_amount` 是**不含税**合计（= 含税 − 税额）。
    已按文档口径实现：`totalAmount` ← 不含税、`finalAmount` ← 含税、`taxAmount` ← 税额；列表列标签暂未跟着改。
    **利润**：全库无 `profit` 列，但两个模块情况不同 ——
    - **报价单**：`QuotationRespVO.profit` 是后端按明细真实算出来的
      （`QuotationServiceImpl.profitOf(items, products)` 走 `MoneyCalculator`），列表那一列**有数据**
    - **合同**：「整单利润」列**已移除**。`crm_contract` 无 profit 列、后端也不返回该字段，
      这一列永远拿不到数据（BUG-002 修复时一并清理，`contract/index.vue` 与 `audit.vue`）

18. **回填按 `emptyForm` 裁剪字段**（`useFormDialog.pickFormFields`）—— 传进来的行/详情对象往往比表单大得多：
    列表行带 `creator` / `createTime` / `starred`，详情对象还带明细、附件、时间线。
    以 `emptyForm` 的键为准筛一遍，提交的 payload 才只包含表单字段。
    **新增字段时记得同步加进 `emptyForm`**，否则编辑回填时会丢。

19. **`build` 通过 ≠ 代码能跑** ⚠️ —— 抓到过两次构建完全发现不了的错误：
    - `onAction({ key, ids, clear })` 解构里漏了 `rows`，函数体却用了 `rows[0]` —— 点「编辑」直接 `ReferenceError`
    - `leadToPool()` 用了 `nextId` 但 import 时漏了它 —— 点「放入线索池」直接 `ReferenceError`

    rollup 不会对「用了没声明的全局变量」报错。**改完 api / onAction 后跑一遍 `npm run check:mock`**，
    它是目前唯一能覆盖 api 层的检查。

    改完列表页/详情页的 `onAction` 后，还可以顺手过一遍：
    ```bash
    for f in $(grep -rln "function onAction" src/views); do
      grep -o "onAction({[^}]*}" "$f" | grep -q rows || grep -qE "\brows\[" "$f" && echo "检查 $f"
    done
    ```
    同类还有：模板里用 kebab-case（`<config-form-dialog>`）引组件时按驼峰 grep 会误判成死 import。

20. **有两处请求体是前端推断的，文档没给字段** ⚠️ —— 接后端时必须核对，别当成已定稿：
    - `PUT /auth/password`（修改密码）—— 按通行做法取的 `{ oldPassword, newPassword }`
    - `POST /crm/opportunity/{id}/products`（添加产品）—— 按明细行数组提交（`ProductItemEditor` 的形状）

    文档里**给了**字段的那些接口是可靠的，可以照抄：
    `/crm/contract/{id}/audit` 的 `{ result, comment }`、`/finance/invoice/{id}/issue` 的
    `{ invoiceNo, issueDate, attachmentIds }`、`/crm/lead-pool/{id}/assign` 的 `{ ownerUserId, reasonRemark }`。

21. **子表数据别做成「全局共享一份」** ⚠️ 同一个坑踩过三次 ——
    联系人、开票信息、公海/线索池行，最初都是**整个项目共用一份数组**，后果是：
    - 每个客户详情页看到的联系人/开票信息一模一样，增删改全串在一起
    - 公海行的 id 和客户 id 撞车（1..18 vs 1..30），池里出现两行同 id，
      `removeById` 只删得掉一行，另一行变成删不掉的幽灵

    真实表都有 `customer_id` / `lead_id` 外键，mock 要用 **map 按外键分组**
    （`contactsByCustomer` / `invoiceInfoByCustomer`），或者让子行**有自己的主键 + 指回父行的外键**
    （公海行的 `id` 另生成、`customerId` 指回客户）。改这类数据前先问一句：
    「这份数据是每个客户一份，还是全局一份？」

22. **`model.id` 才能判断「是编辑不是新增」** ⚠️ —— 字段配置里写
    `disabled: (model) => !!model.id` 用来锁住不该改的字段（人员的账号、字典的类型、角色的标识）。
    `useFormDialog` 回填时按 `emptyForm` 裁剪字段，**`id` 不在 emptyForm 里，差点就漏放了**——
    漏放的话这个判断恒为 false，禁用形同虚设，而且**不报任何错**。
    已修：`pickFormFields` 单独放行 `id`（提交时 `submit()` 会再摘掉，不会发给后端）。
    新增字段时同理，记得同步加进 `emptyForm`。

27. **页面级权限是两层，别只看到一层** ⚠️ —— `src/router/index.js` 的守卫里有两道：
    - **第一层（隐式）**：未授权的菜单根本不会生成路由，手动敲 URL 会落到兜底的
      `/:pathMatch(.*)*` → `/404`。这一层不需要额外代码，是 `generateRoutes` 的自然结果
    - **第二层（显式）**：守卫里按 `to.meta.perms` 调 `userStore.hasPermission()` 再兜一道，
      防的是「路由在、但权限标识对不上」

    ⚠️ **第二层必须放在「动态路由生成」那个分支之后**。首次导航时路由还没生成、
    `to.meta` 是空的，此时校验毫无意义且会把所有导航误判成无权限；
    `next({...to, replace: true})` 会重新进守卫，**那一次**的 `to.meta.perms` 才是真实值。
    （`perms` 为空就放行 —— `/login`、`/404`、Layout 容器路由都没有它。）

    无权限时跳 **`/404` 而不是 403 页**：不泄露「这个资源存在但你没权限」，与后端
    「越权访问某条数据返回『不存在』而不是『无权限』」是同一套取舍。

28. **`emptyForm` 的键之间不能夹注释（行尾注释也不行）** ⚠️ ——
    `check:static` 的「每个 FIELDS 的 prop 都被对应的 emptyForm 覆盖」这一项，
    靠 `(?:^|[,{])\s*(\w+)\s*:` 提取键名 —— **它要求逗号/花括号后面只有空白、紧接键名**。
    一旦在键之间插了注释，**注释后面的那个键就提取不到**，于是误报「emptyForm 缺 xxx」：

    ```js
    emptyForm: () => ({
      deptIds: [],
      // 这行注释会让下面这个键提取不到 → 误报「缺 groupName」
      groupName: '',
      groupId: null, // 行尾注释也会让 remark 提取不到 → 误报「缺 remark」
      remark: ''
    })
    ```

    这不是检查器的 bug（它的目的是抓「FIELDS 里加了字段但忘了加进 emptyForm」这个真实的坑），
    而是它正则的已知局限。**要写说明就写在 `emptyForm` 对象外面**，别写在键之间。

29. **算术验证码：进登录页就标红是 `validate-on-rule-change` 干的** ⚠️ ——

    `rules` 是 `deep: true` 的 watch、且 `validate-on-rule-change` **默认为 true**，
    于是 `onMounted` 拿到验证码、`captchaEnabled` 一变，表单立刻对全部空字段跑一次校验 ——
    表现就是「刚进登录页、什么都没填，输入框全红了」。
    修法是给那个 `el-form` 显式写 `:validate-on-rule-change="false"`。

30. **兜底路由必须带 `name`，且不能用 `redirect`** ⚠️ 已修（详见后端 `docs/07-测试BUG记录.md` BUG-001）——
    曾经的现象：**每换一个账号登录，落地页必定是 404，刷新也出不来**，只能点「返回首页」。
    两个原因叠加：

    - **匿名路由删不掉**：注册兜底路由时没写 `name`，而 `resetRouter()` 是按 `name` 删的
      （`catchAll.name` 是 `undefined`）。`vue-router` 的 `insertMatcher()` 里是
      `if (matcher.record.name && ...) matcherMap.set(...)` —— **匿名路由不进 `matcherMap`**，
      所以实际执行的是 `removeRoute(undefined)`，只打一句 `Cannot remove non-existent route`
      就返回，兜底路由会一直残留到下次刷新。
    - **`redirect` 在守卫之前就被解析**：`pushWithRedirect()` 里 `handleRedirectRecord()`
      的执行**早于** `navigate()`（跑 `beforeEach` 的那一步）。于是换账号后
      `router.push('/dashboard')` 会先被残留的兜底路由改写成 `/404`，**守卫拿到的
      `to.path` 已经是 `/404`**，来不及注册新账号的路由，`next({...to})` 也就稳稳定在 404。

    ```js
    router.addRoute({
      path: '/:pathMatch(.*)*',
      name: 'CatchAll',                                   // 不加就删不掉
      component: () => import('@/views/error/404.vue'),   // 不能用 redirect，否则抢跑守卫
      meta: { title: '页面不存在', hidden: true }
    })
    ```

    **凡是靠守卫动态注册路由的方案，都别用 record 级 `redirect` 做兜底** —— 它一定比守卫先执行。
    同理，`router.addRoute()` 加的路由一律给 `name`。

    与第 27 条同源（都是**守卫执行顺序**的坑），改守卫时两条一起看。

31. **前端放行 ≠ 后端放行：超管判断两边口径不同** ⚠️ 已修（详见后端 `docs/07-测试BUG记录.md` BUG-003）——
    曾经的现象：**超管账号登录后首页看板是空壳** —— 页面正常打开、菜单也正常，
    但 `/dashboard/*` 8 个接口**全部 403**。而销售、财务这些**低权限**角色一切正常。

    **前端这一侧本来就是对的**，问题在于两边对 `*:*:*` 的理解不一致：

    - **前端**：`store/user.js` 的 `hasPermission()` 是**显式**判断，
      直接 `this.permissions.includes('*:*:*')` 就放行 —— 不依赖任何通配匹配语义。
    - **后端**：`@SaCheckPermission` 交给 Sa-Token 的 `SaFoxUtil.vagueMatch` 做**通配匹配**，
      而模式里的 `:` 是**字面量**，所以 `*:*:*` 默认只能命中三段式权限码
      （`crm:lead:list`），**命中不了两段式的 `dashboard:view`**。

    两者一叠加，就得到最难排查的那种**半坏**状态：**路由守卫放行、页面能打开、接口全部报错**。
    因为既不是 404、也不是菜单不显示，很容易往「菜单配置 / 看板数据权限」方向跑偏。

    **怎么用这条**：

    - 遇到「页面进得去、但数据全空或全 403」，**先看 Network 面板**，别先怀疑路由和菜单 ——
      路由与菜单是前端说了算的，数据是后端说了算的，**两者可以不一致**。
    - `hasPermission()` 放行**只代表前端不拦**，不代表后端会给数据。别把它当成「有权限」的完整证明。

    后端已在 `SaTokenConfig#overridePermissionMatching()` 里把 `*:*:*` 显式钉成「全部权限」，
    **前端无需改动**。与第 27 条（页面级权限两层）一起看。

34. **密码框的 `autocomplete` 要按语义标，`off` 是没用的；`el-dialog` 里的表单必须清值** ⚠️ 已修
    （详见后端 `docs/07-测试BUG记录.md` BUG-022）——

    用户报「点注册后输入框里就有默认值」。查下来是**两个独立原因叠加**：

    **① 浏览器密码管理器填充。** 浏览器看到「文本框 + 密码框」就当登录框填。
    ⚠️ 关键坑：**Element Plus 的 `ElInput` 自己声明了 `autocomplete` prop，默认值就是 `off`**
    （并绑到原生 `<input>`）—— 所以那些框**本来就带着 `off`**，
    而 **Chrome 对密码框上的 `off` 基本无视**。
    也就是说「明明写了 `off` 还是被填」是正常的，不是没生效。**必须用 `new-password`。**

    | 场景 | 该用的值 |
    | :--- | :--- |
    | 设新密码（注册 / 找回 / 改密） | `new-password` |
    | 输入现有密码（登录） | `current-password` |
    | 登录账号 | `username` |
    | 邮箱 / 验证码 | `off` |

    **登录页与注册弹窗要标成一对**：登录标 `current-password`、注册标 `new-password`，
    两边都标清楚，浏览器才不会把「注册」当成「登录」来填。

    **② 弹窗没销毁，表单值留在内存里。** `el-dialog` 默认 `destroy-on-close=false`，
    内容不销毁；而 `form` 是 setup 里的 `reactive` 对象。所以
    「填一半 → 取消 → 再打开」会留着上次的输入。

    **怎么用这条**：

    - **`el-dialog` 的 `@open` 里要清值，不能只 `clearValidate()`。** 这个 bug
      **无痕模式也能复现**，所以「换个浏览器就没事」不代表这类问题不存在 ——
      反过来说，**要区分这两个原因，就用无痕窗口试**：还复现就是 ②，不复现就是 ①。
    - **别把「属性写了没有」当成「防住了没有」。** 组件库可能已经帮你默认了一个值，
      于是「加过」和「没加」看起来一模一样，而问题依然在。**要验的是实际行为。**
    - 表单初始值抽成 `EMPTY_FORM` 常量（`Object.assign(form, EMPTY_FORM)` 重置），
      不要在「初始化」和「重置」两处各抄一份字面量 —— 加字段时必然漏一处。

35. **限流/倒计时状态必须和后端同一个「维度」；别用禁用按钮表达「输入不合法」** ⚠️ 已修
    （详见后端 `docs/07-测试BUG记录.md` BUG-023）——

    用户报「有的时候获取不到验证码（注册时）」。查下来是**两个独立原因**，
    而它们表现出的症状一模一样，所以很难从现象区分：

    **① 倒计时粒度与后端不一致。** 后端限流 key 是 `auth:email:limit:{email}` ——
    **按邮箱**限 60 秒，且登录/注册/找回密码**三入口共用同一把锁**；
    而前端倒计时原本**按入口各持一份**。于是「登录页给 A 发过码 → 注册页再给 A 发」
    直接撞后端 1004，**而按钮上没有任何倒计时**，用户不知道为什么发不出去。
    → 已改为**按邮箱共享**倒计时（`sessionStorage` 兜一层，刷新后仍在）。

    **② 邮箱稍不合法时按钮是个「死按钮」。** `canSend()` 里带了 `isValidEmail`，
    而按钮绑 `:disabled` —— 填 `abc@qq`（少个点）按钮就灰了，
    **点下去既没反应也没有任何提示**。比 ① 更糟：① 至少还有一句报错。

    **怎么用这条**：

    - **前端做限流/倒计时，先问一句「后端是按什么维度限的」。** 两边维度不一致时，
      前端要么比后端宽松（用户撞限流且无提示），要么比后端严格（明明能发却发不出）。
    - **别用「禁用按钮」表达「输入还不合法」** —— 置灰的按钮没有任何解释能力。
      合法性应在点击后给提示，而不是把按钮变灰。
    - **失败要能区分「可以立刻重试」和「该锁一会儿」**。本例里 1009（发信失败）
      后端**会退还限流**，前端就**绝不能**再自己锁 60 秒（否则用户既没收到信又被拦住重发）。
      判断依据是 `error.bizCode`（`request.js` 现在会把业务码挂上去，
      **别靠匹配中文文案** —— 文案一改判断就静默失效）。

      连带清掉报价单与产品 —— 因为合同那边的报价单选择器是**按商机过滤**的，留着不匹配的报价单
      会自相矛盾。

      ⚠️ 报价单表单的**回显只在「用户选中商机」时发生**：`form.opportunityId` 在**编辑回填**时
      同样会变，回显若无条件执行，用户一打开编辑弹窗、什么都没做，已保存的客户/负责人/**产品明细**
      就会被商机上的值顶掉。做法是商机字段 `onSelect` 置一个 `pickedOpportunity` 标记，
      由既有的 `watch` 决定要不要回显 —— **别把那个标记当成多余的死代码删掉**。

      ⚠️ 明细行的映射（后端 `DocumentItemRespVO` → `ProductItemEditor`）只有一份，在
      `utils/documentItems.js`；合同表单与报价单表单共用，**不要再复制第二个副本**
      （复制出来必然漂移，见下面第 33 条的反面教材）。

    **怎么用这条**：改任何一边的联动规则，另一边必须一起改，否则用户会撞到
    「保存被 2304 / 2253 拒掉」或者「界面显示 A、落库 B」。客户不一致时后端**拒绝而不是静默改写**
    （改客户会连带改数据权限），所以前端把客户置成了只读 —— 别把那个 `disabled` 当成多余的、
    顺手删掉。另外「商机有报价单时必须先建报价单才能录合同」**不是**本项目的规则：
    `opportunity_id` / `quotation_id` 都可空，客户直签、商机直签都是合法流程。

37. **审批进度（该谁审 / 下一步到谁）由后端一处提供，前端不要自己推断** ⚠️ ——
    合同审核期间 `auditStatus` **一直是「审核中」**（流程是两级：部门主管 → 财务），
    只有最后一个节点通过才会变成「审核通过」。所以这两件事**必须**来自后端：

    | 入口 | 内容 |
    | :--- | :--- |
    | `GET /crm/contract/{id}/approval` | 节点顺序、每步谁审的（含意见与时间）、当前环节与待办人、**下一步节点与预计审批人**、数据异常提示 |
    | `GET /crm/contract/audit-list`（每行） | `currentNodeName` / `pendingApproverNames` / `nextNodeName` / `nextApproverNames` / `applyUserName` / `applyTime` |

    页面见 `views/crm/contract/ApprovalProgress.vue`（**合同审核页的弹窗**与**详情页的「审批进度」Tab** 共用）。

    ⚠️ **「提交人」不是「创建人」**：`applyUserName` 是点「提交审核」的人（审批实例的发起人），
    `creator` 是建单人 —— 单据可以甲建乙提交，合同审核页那两列要的是前者。

    ⚠️ **审批人解析只有后端一份实现**（`ContractServiceImpl#resolveApprovers` 与预解析用的
    `predictApprovers` 逐条对应），**前端不许自己按角色 / 上级去猜**：猜错了界面就会指着
    一个永远收不到待办的人。`预计审批人` 是**预计** —— 组织架构、角色成员、流程配置变了就不一样，
    文案别写成「即将审批人」；它为空时是**配置问题**（角色下无成员、发起人没有直属上级），
    界面上要显式写「未解析出审批人」，不要静默留空。

    ⚠️ 进度弹窗与详情 Tab 都用 `v-if` 控制组件挂载来强制重新取数（同一个弹窗连续打开不同行时，
    组件不销毁会一直显示上一行的数据）—— 别改成 `destroy-on-close`（第 12 条）。
